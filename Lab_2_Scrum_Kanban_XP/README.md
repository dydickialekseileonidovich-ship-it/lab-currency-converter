## 1. Блок Scrum

### 1.1. Карта стейкхолдеров (Stakeholder Map)
В системе задействовано множество ролей со специфическими интересами и полномочиями:

| Стейкхолдер / Роль | Интересы и цели | Влияние / Вовлечённость |
|---|---|---|
| **Студенты** | Простая подача документов, прозрачные критерии, мгновенное отслеживание статуса заявки без очередей | Высокое влияние на продукт, ключевые пользователи |
| **Деканат / Замдекана по учебной/воспитательной работе** | Проверка академической успеваемости, валидация поданных документов и оснований, согласование заявок | Высокое влияние, согласующая сторона |
| **Стипендиальная комиссия факультета / вуза** | Финальный отбор кандидатов на повышенные стипендии по рейтингу, формирование протокола | Высокое влияние, лица, принимающие решения |
| **Бухгалтерия / Расчётный отдел** | Получение выверенного реестра на выплату, соответствие стипендиальному фонду, отсутствие заблокированных счетов | Среднее/высокое влияние, финансовый контроль |
| **Профком студентов** | Контроль прозрачности и соблюдения прав студентов льготных категорий | Консультативная и надзорная роль |
| **Системные администраторы вуза** | Интеграция с университетской LDAP/Active Directory, безопасность персональных данных | Техническое обеспечение |

### 1.2. Роли в Scrum-команде
- **Product Owner (PO):** Замдекана/представитель учебно-методического управления. Управляет бэклогом, выставляет бизнес-приоритеты, согласовывает требования с бухгалтерией и профкомом.
- **Scrum Master (SM):** Фасилитирует процессы, устраняет блокеры (например, задержку утверждения форм регламентов деканатом), проводит ретроспективы.
- **Developers (Кросс-функциональная команда):** 2 backend-разработчика, 1 frontend-разработчик, 1 QA-инженер, 1 DevOps.

### 1.3. Product Backlog с MoSCoW-приоритизацией

#### Must have (Критически важный MVP к началу сессии)
1. **US-01:** Аутентификация студента через личный кабинет вуза.
2. **US-02:** Электронная форма подачи заявления на стандартную академическую и социальную стипендии с загрузкой сканов/PDF.
3. **US-03:** Личный кабинет сотрудника деканата для проверки комплекта документов и выставления вердикта («Принято», «Отклонено», «Требуется доработка»).
4. **US-04:** Экспорт утверждённых списков в Excel/CSV для бухгалтерии.

#### Should have (Важно для эффективности, но не блокирует базовый запуск)

6. **US-06:** Валидация форматов и размеров файлов на клиенте и сервере (ограничение до 15 МБ, форматы PDF/JPG/PNG).
7. **US-07:** Автоматическая проверка среднего балла по базе деканата.

#### Could have (Полезные расширения при наличии ресурсов команды)

9. **US-09:** Чат/комментарии между модератором деканата и студентом по спорным документам.

#### Won't have (Отложено на будущие релизы)

11. **US-11:** Автоматическое OCR-распознавание текста справок о доходах.

### 1.4. Ритм спринтов (Sprint Cadence)
- Длительность спринта: 2 недели.
- **Sprint Planning:** Отбор историй из верхушки бэклога в соответствии со скоростью команды (Velocity ~ 28 Story Points).
- **Daily Scrum:** 15-минутные стендапы: что сделано, фокус на день, блокеры внешних согласований.
- **Sprint Review (Демо):** Демонстрация рабочего инкремента представителям деканата и студенческому активу.
- **Sprint Retrospective:** Анализ проблем взаимодействия и технических узких мест.

## 2. Блок Kanban

### 2.1. Доска задач и WIP-лимиты
Из-за специфики предметной области (зависимость от подписей деканатов и регламентов бухгалтерии) ключевой особенностью является колонка **Waiting for stakeholder**.

```
+---------------+---------------+---------------------------+---------------+---------------+---------------+
| Backlog (∞)   | Ready (5)     | In Progress (3)           | Waiting for   | Testing (2)   | Done (∞)      |
|               |               |                           | stakeholder(3)|               |               |
+---------------+---------------+---------------------------+---------------+---------------+---------------+
| TASK-108      | TASK-105      | TASK-103: Форма загрузки  | TASK-101:     | TASK-102: API | TASK-098      |
| TASK-109      | TASK-106      | документов льготников     | Согласование  | авторизации   | TASK-099      |
| TASK-110      | TASK-107      |                           | формы реестра | через LDAP    | TASK-100      |
|               |               | TASK-104: Валидатор       | бухгалтерией  |               |               |
|               |               | размера PDF-файлов        |               |               |               |
+---------------+---------------+---------------------------+---------------+---------------+---------------+
```

### 2.2. Политики перехода (Definition of Done и Exit Criteria)
- **Ready -> In Progress:** Назначен исполнитель, критерии приёмки зафиксированы, нет неразрешённых архитектурных вопросов.
- **In Progress -> Waiting for stakeholder:** Задача блокирована отсутствием внешнего ответа (например, утверждённый шаблон заявления от юристов или формат реестра выплат от бухгалтерии). Указывается конкретный контакт и дата запроса. Если лимит (3) превышен, Scrum Master подключается эскалацией к PO.
- **Waiting for stakeholder -> In Progress:** Ответ/решение получено, задача возвращается разработчику.
- **In Progress -> Testing:** Код покрыт юнит-тестами, сделан PR, CI прошёл успешно.
- **Testing -> Done:** Автотесты и ручной смоук-тест пройдены, ветка смержена в main, задеплоена на staging-стенд.

### 2.3. Узкие места и управление потоком
- **Колонка `Waiting for stakeholder` (WIP = 3)** — основная точка риска: согласования с деканатом и бухгалтерией могут затягиваться. Для каждой карточки фиксируется дата запроса и ответственный; при простое более 2 дней Scrum Master эскалирует блокер через PO.
- **Колонка `Testing` (WIP = 2)** — защищает единственного QA-инженера от «завала» в конце спринта (при заполнении разработчики подключаются к написанию автотестов).
- Подробный срез доски с оценками в Story Points и легендой вынесен в [board.md](board.md).

## 3. Блок Extreme Programming (XP)

### 3.1. Практика 1: User Stories с критериями приёмки (Acceptance Criteria)
Каждая задача описывается с позиции пользователя с чётким набором проверяемых условий.
- **Пример Story:**
  * *Как студент, имеющий достижения в научно-исследовательской деятельности,*
  * *Я хочу прикрепить электронные копии дипломов и список публикаций к заявке на повышенную стипендию,*
  * *Чтобы стипендиальная комиссия учла мои баллы при рейтинговании.*
- **Критерии приёмки (Acceptance Criteria):**
  1. Допускается загрузка файлов форматов `.pdf`, `.png`, `.jpg` суммарным объёмом не более 20 МБ.
  2. Для каждой публикации обязательно заполнение полей: Название статьи, Библиографическое описание (РИНЦ/ВАК), Год.
  3. При успешной отправке заявке присваивается статус `SUBMITTED`, а студенту выдаётся регистрационный номер и дата подачи.

### 3.2. Практика 2: Небольшие частые релизы (Small Releases)
- Вместо полугодового цикла водопадной разработки команда выпускает работающие инкременты каждые 2 недели.
- **Релиз 0.1:** Студент может войти и отправить заявление на базовую академическую стипендию.
- **Релиз 0.2:** Деканат получает кабинет модерации и может проставлять статусы заявкам.
- **Релиз 0.3:** Подключена социальная стипендия с загрузкой сканов справок из соцзащиты.
- **Эффект:** Быстрая обратная связь от пользователей; минимизация риска выпустить непригодную систему прямо в разгар подачи заявлений.

### 3.3. Практика 3: Непрерывная интеграция (Continuous Integration)
- Разработчики сливают ветки в общий репозиторий не реже одного раза в день.
- На каждый коммит и Pull Request настроен автоматический запуск пайплайна: линтеры (flake8/black), юнит-тесты (pytest), проверка миграций БД и сборка тестового Docker-образа.
- **Риск без практики:** «Интеграционный ад» в конце спринта, когда конфликтуют изменения схемы базы данных и логики маршрутизации статусов от разных разработчиков.
